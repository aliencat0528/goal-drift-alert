# 決策流程

> 本檔記「什麼時候該說話、說什麼、怎麼確保沒說錯」。
> 參數值的正本在 `config/params.yaml`，本檔只解釋規則與理由。

## 核心公式

```
V = P(風險為真) × 未處理損失 × 剩餘可行動時間比例 × 可救性 − 打斷成本

發送條件：V > gate.min_value        發送順序：V 由大到小，取前 gate.daily_quota 則
```

| 項 | 目標偏移怎麼算 | 待辦怎麼算 |
|----|--------------|-----------|
| `P(風險為真)` | Monte Carlo 輸出的 P(達不到)。**天生是機率，不需校準** | P(逾期) = 1 − S(t)，來自生存模型（M2） |
| `未處理損失` | `unit_value × 預估缺口`，無金額時走 `interrupt_only` | `deadline_miss` 固定罰則 × 不可逆性權重 |
| `剩餘時間比例` | `(deadline − now) ÷ (deadline − start)`。**天生就有** | 同左 |
| `可救性` | required rate 是否還在能力範圍內，見下 | 剩餘時間 vs 同類歷史耗時中位數 |
| `打斷成本` | `gate.interrupt_cost` | 同左 |

### 為什麼要有「可救性」這一項

它是目標偏移獨有的。有些目標現在救還來得及，有些已經數學上不可能——
**不可能的那些不該發警示，該發「建議改目標」**。

```
可救性 = 1                      當 required_rate ≤ 歷史最佳 P90
       = 線性遞減               當 required_rate 介於兩者之間
       = 0（改走「建議改目標」）  當 required_rate > 歷史最佳 × drift.infeasible_multiple
```

> **可救性歸零的那則仍然要競爭配額**：它是「建議改目標」，不是「不說」。
> 但它的 V 必為負（乘以 0 再扣打斷成本），所以排序改用**賭注**
> （`P × 損失 × 剩餘時間比例 − 打斷成本`，即拿掉可救性那一項）——
> 否則所有已經救不回來的目標都會排在最後面，而它們正是最急著要你做決定的那些。

沒有這一項，系統會在最後三天每天提醒你一件已經做不到的事——
那是最典型的、也最快讓人關掉通知的失敗模式。

## 四個觸發（目標偏移）

| 觸發 | 條件 | 為什麼重要 |
|------|------|-----------|
| **可行性翻轉 ★** | required rate 首次超過歷史最佳 run rate 的 `drift.feasibility_percentile` | 目標從「困難」變成「以你的歷史表現不可能」。**這是唯一真正需要立刻知道的時刻**，因為它是還來得及改目標的最後窗口 |
| 趨勢反轉 | EWMA 或 CUSUM 偵測到 run rate 階躍下降 | 你的產出掉了，但你沒發現 |
| 緩衝耗盡 | pace ratio 連續 N 期低於門檻，或 fever chart 進紅區 | 傳統但有效 |
| 靜默期 | 無進展天數 > 歷史間隔的 `drift.silence_percentile` | 抓「這個目標已經死了，但你還沒承認」 |

## 三個不該警示的時刻

| 不發 | 條件 | 理由 |
|------|------|------|
| 期初 | 時間消耗比 < `gate.early_period_ratio` | 第一週投 0 份，pace ratio = 0，但那完全正常。**早期雜訊極大，此時警示只會製造不信任** |
| 剛達成里程碑後 | 前 3 天內有大於 P75 的 delta | 短期 run rate 天然會掉 |
| 只是落後 | required rate 仍在歷史正常範圍內 | 落後不需要打斷你，不可能才需要 |

## 待辦與目標的連結規則

待辦警示**不是獨立管線**，三條規則把它接回風險決策：

1. **共用配額**：待辦與目標的候選警示放進**同一個排序**，一起競爭 `gate.daily_quota`。
   一件快到期的待辦可以擠掉一個目標偏移警示，反之亦然。
   **若兩者各有配額，總量翻倍，警示疲勞照樣發生**
2. **向上彙總**：待辦延遲會推高父目標的 required rate。
   計算順序固定為 `tasks → goals`，**所以待辦延遲是目標可行性的領先指標**
3. **向下歸因**：目標觸發可行性翻轉時，決策卡**必須**列出貢獻最大的 2–3 件待辦。
   只說「來不及了」而不說「卡在哪」的警示不可行動，依 SRE 原則就不該發

### 去重規則

同一根因的多則合併成一則。判定順序：

```
同一 goal_id 的多個觸發        → 合併，取 V 最高者當標題，其餘列為證據
父子目標同時觸發               → 只發父目標，子目標列為證據（避免月/週/日發三次）
同一 task 的多個原型判定       → 取最嚴重者
```

## 五道關卡（確保結果符合情境）

> **沒有任何人能「確保」分析符合情境。能設計的是讓錯誤在便宜的時候暴露出來的流程。**

情境錯誤有三種，各有不同的抓法：

| 錯誤型態 | 例子 | 誰抓得到 |
|---------|------|---------|
| 統計錯誤 | 比率型用了連續型偵測器；分母太小 | ✅ 機器（關卡 1） |
| 語意錯誤 | 「已投遞」其實包含了「已收藏」 | ✅ 回放時人一看數字就知道不對（關卡 2） |
| **價值錯誤** | 統計完全正確，但這件事根本不值得打斷你 | ❌ **機器永遠抓不到，只有人** |

| 關卡 | 誰做 | 抓什麼 |
|------|------|-------|
| **0 契約靜態檢查** | 機器 | 目標自相矛盾：`deadline < start_date`（同一天合法，日目標就是這樣）、比率型配絕對金額損失、`target ≤ 0`、`parent_id` 不存在或成環 |
| **1 資料體檢** | 機器 | 資料量對照 `cold_start.min_points`、分母是否足夠、snapshot 有無斷天 |
| **2 歷史回放 ★** | **機器算，人判斷** | 拿過去 90 天跑一次：「會發哪幾則、當時什麼情況」 |
| **3 影子模式** | 系統跑，人不被打擾 | `cold_start.shadow_days` 天只寫進 dashboard 不推播 |
| **4 分級發布** | 機器 | 前 `ramp_up_days` 天只發最高分 1 則；誤報率超標自動退回影子模式 |
| **5 持續監控** | 機器盯，人決定 | precision、被忽略率、「太晚了」比例、**靜音率** |

> **關卡 1 擋的是「該偵測器能不能用」，不是「這則能不能發」**（← `prepare.md` AG-008）。
> Monte Carlo 資料不足時卡片照發，但三個選項的機率一律標「—」並寫明還差幾天——
> 門檻存在的目的是不畫一條假裝可信的線，不是讓系統閉嘴。
>
> 回放（關卡 2）就是 `--as-of`：`python3 -m compute.report --as-of 2026-08-24` 會**只用那天以前的資料**
> 重跑一次。固定的模擬種子（`forecast.random_seed`）讓同一份資料每次跑出同一張卡，
> 否則改了參數之後，你分不出差異是參數造成的還是抽樣造成的。

### 關卡 2 是整個流程的樞紐

使用者**沒有能力**評估「EWMA 的 lambda 該設 0.2 還是 0.3」。
但他**百分之百有能力**評估「這則警示我當時想不想收到」。

> **回放的真正作用，是把一個人答不出來的問題（模型對不對），
> 換成一個人一定答得出來的問題（這則我要不要）。**

這就是「誰來做」的答案：使用者只負責回答價值問題，機器負責全部技術問題，
而回放是把技術問題翻譯成價值問題的那台機器。

## Trust Ledger：三顆按鈕

每則警示強制附三個結果，**刻意沒有「已讀」**——已讀不產生任何學習訊號。

| 按鈕 | 系統學到什麼 |
|------|------------|
| **已處理** | 該觸發規則的先驗命中率上調，門檻放寬 |
| **不用理** | 誤報率上調 → 門檻升高。連續 `gate.auto_mute_after_dismiss` 次即自動靜音該規則 |
| **太晚了** | 可行動時間窗被證明太短 → 該規則的觸發點前移 |

月報固定回答兩句：**本月幫你擋掉 X 則、抓到 Y 則、其中 Z 則你說太晚了。**
擋掉的必須被看見——否則使用者只會覺得系統很安靜，然後懷疑它壞了。

---

## 三個逃生出口（任何時候都在）

1. **靜音這條規則**——不是關掉整個系統
2. **降回影子模式**——保留資料，只是不吵你
3. **看見完整推導**——「為什麼發這則」要能一路展開到原始數字

第三個尤其關鍵，而且它反過來支持「v1 不用 ML」的決定：
**黑箱模型會剝奪使用者判斷情境對錯的能力**，而情境判斷是本系統唯一無法自動化的部分。

---

## 誠實的產品承諾

本系統**不保證**分析符合情境。它保證的是：

> **不符合情境時，你會很快發現，而且發現的成本很低。**

回放讓你在啟用前發現，影子模式讓你在被打擾前發現，靜音率讓系統在你放棄前發現。
