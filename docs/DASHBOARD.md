# Dashboard 設計

> 本檔記視覺化的資訊架構與各視圖規格。
> **配色與圖表細節在 M4 實作時依 `dataviz` 規範定案**，本檔只定結構、編碼方式與取捨理由——
> 現在寫死 hex 只會在實作時被推翻一次。

## 這個 dashboard 要解決的問題

它**不是**一個「看數字」的地方。決策卡已經把該說的話說完了，dashboard 存在的理由只有三個：

1. **看被擋掉的那些**——沒有這個，使用者無從判斷系統是安靜還是壞了
2. **在被打斷之前自己來看**——影子模式期間唯一的出口
3. **看趨勢而不是看當下**——決策卡講今天，dashboard 講這個月怎麼走過來的

> **推論：這代表 dashboard 的主角是「歷史與被擋掉的」，不是「即時狀態」。**
> 多數個人儀表板做反了——把最醒目的位置給了當下數字，
> 而當下數字正是決策卡已經處理掉的那一塊。

## 設計原則

| 原則 | 落地 |
|------|------|
| **摘要在細節之前** | 進頁面第一屏是決策卡與 fever chart，任何單一目標的細節都要捲動或點擊 |
| **狀態編碼在形狀，不只在數字** | 嚴重度用色條 ＋ 標籤 ＋ 位置三重編碼，不能只靠顏色（色盲與列印） |
| **語意色與品牌色分離** | `critical`／`warning`／`ok`／`neutral` 是語意角色；主色不參與嚴重度編碼 |
| **沒命中就整塊不顯示** | 今天沒有警示就不畫警示區，**不顯示「今日無異常」的空狀態卡**——湊數是壁紙化的第一步 |
| **不確定要明說** | 資料不足的偵測器在該區塊標「校準中（還差 N 天）」，不畫一條假裝可信的線 |
| **數字對齊** | 所有數字欄位用 tabular-nums，比較大小靠視覺不靠讀 |

## 資訊架構（由上而下）

```
┌─ ① 今日決策卡（0–3 張，沒有就整塊不顯示）
├─ ② Fever Chart — 所有目標一張圖  ★ 主視圖
├─ ③ 待辦風險矩陣
├─ ④ 目標詳情（Burn-up + 預測扇形），每個目標一張，可摺疊
├─ ⑤ 求職漏斗
├─ ⑥ EWMA 控制圖（進階，預設摺疊）
├─ ⑦ 今日摘要 — 被擋在配額外的那些
└─ ⑧ Trust Ledger 月報
```

## ① 今日決策卡

規格見 `DECISION-FLOW.md`。視覺上的三個要求：

- 嚴重度色條在**左緣**，不是整張卡染色（整張染色會讓文字對比不可控）
- 「不做的後果」與其他選項**同等視覺權重**——它是最容易被跳過、卻最該被看見的一項
- 三顆回饋按鈕在卡片底部，**沒有「已讀」**

## ② Fever Chart ★ 主視圖

借關鍵鏈專案管理（CCPM）的緩衝發燒圖。**這是整個 dashboard 唯一必看的圖。**

```
Y = 緩衝消耗 %（= 1 − 可救性，或 required/歷史最佳 的正規化）
X = 進度完成 %（attainment rate）

  100 ┤ ▓▓▓▓▓▓▓▓▓▓  ← 紅區：不可能了，該改目標
      │ ▓▓▓▓▓▓░░░░
   50 ┤ ▓▓▓░░░░░░░  ← 黃區：要加速
      │ ░░░░░░░░▒▒
    0 ┼──────────── ← 綠區：照這樣就好
      0    50   100 %
```

**為什麼是這張圖當主視圖**：它是唯一能把**所有目標放在同一張圖上比較**的形式。
Burn-up 每個目標要一張，看五個目標要看五張圖，而人不會看五張圖。

- 一個目標 = 一個點，標籤是目標名
- **畫出軌跡尾巴**（過去 7 天的位置），讓「正在往紅區走」與「已經在紅區但穩住了」分得開
  ——這兩者的正確動作完全不同，而靜態的點分不出來
- 三色區是背景填色，點本身用中性色，靠**位置**傳達嚴重度

## ③ 待辦風險矩陣

散點圖，直接把三種風險原型畫在同一個平面上。

```
Y = 改期次數 (deferral_count)
X = 任務年齡 (age，天)
點大小 = 下游依賴數
點形狀 = 有無 due_date（懸崖型 vs 其他）

右上角 = 又老又一直改期 → 高風險區
```

- 右上角用淡底色框出「高風險區」，門檻取 `task.age_percentile` 與 `task.deferral_threshold`
- **腐爛型（age > rot_days 且無 goal_id 無 due_date）畫成空心點**，並在圖下方直接列出
  「這 N 件 90 天沒碰過，要一次清掉嗎」——**這是提議刪除，不是警示**
- 有 `goal_id` 的點用連線指向對應目標，讓「哪些待辦卡住哪個目標」看得見
  ——這是待辦與風險決策連結的視覺體現

## ④ 目標詳情：Burn-up ＋ 預測扇形

每個目標一張，預設只展開有警示的那些。

- 實線：累積完成量
- 虛線：理想線（start → deadline 的直線）
- **扇形**：Monte Carlo 的完成預測區間（P15–P85），末端與目標線的關係一眼看出來
- 標註 `required rate` 與 `歷史最佳 P90` 兩條斜率參考線 —— **可行性翻轉就是這兩條交叉的那一刻**
- 資料點不足 `cold_start.min_points.monte_carlo` 時**不畫扇形**，只畫實線與理想線，並標「預測校準中」

## ⑤ 求職漏斗

`觀望中 → 已投遞 → 有回覆` 三階，直接來自 Notion 狀態欄。

- 顯示各階段絕對數 ＋ 階段轉換率
- **可切維度**（公司／求職管道／關聯職位／評估等級），這是現成的歸因維度
- 這一塊的價值不只是求職進度：**它是「求職漏斗 = 行銷漏斗」那座橋的實體**，
  同一段程式碼換資料源就是 impression → click → conversion

## ⑥ EWMA 控制圖（預設摺疊）

run rate 的統計製程管制圖。

- 中心線 ＋ 上下控制界限（`detector.ewma.L` 倍 sigma）
- 觸發 Western Electric 規則的點加標記，並在 tooltip 寫明是哪一條規則
- 標題必須寫明用的是 `run_length: 8`（版本有用 7/8/9，不標會讓結論無法重現）
- 預設摺疊：這是給想深入的人看的，不是每天要看的

## ⑦ 今日摘要：被擋在配額外的

**這一塊的存在本身就是產品主張。** 列出今天算出來但沒發的候選，含各自的 V 值與被擋原因：

| 原因 | 顯示文字 |
|------|---------|
| 擠不進配額 | 「排在第 4 位，今日配額 3」 |
| 期初 | 「時間才過 12%，太早」 |
| 可救性為 0 | 「已不可能達成 → 已改列建議改目標」 |
| 資料不足 | 「校準中，還差 6 天」 |
| 規則已靜音 | 「你連續 3 次說不用理，已靜音」 |

## ⑧ Trust Ledger 月報

固定回答兩句：**本月擋掉 X 則、抓到 Y 則、其中 Z 則你說太晚了。**

加三個趨勢小圖：precision（已處理比例）、被忽略率、靜音率。
**靜音率是最誠實的指標**——使用者關掉它就是最終判決。

## 技術實作

| 項目 | 選擇 | 理由 |
|------|------|------|
| 產生方式 | Python ＋ Jinja2 → 單一 `.html` | 一個檔案，用瀏覽器開就好 |
| 圖表 | **手寫 inline SVG**，不用 plotly／matplotlib | 零外部資源、檔案小、可直接發布成 artifact。圖種類只有 5 種，值得自己畫 |
| 互動 | 極少量原生 JS（摺疊、切維度） | 不引入任何前端框架 |
| 主題 | 淺色／深色雙主題，用 CSS 變數 | — |
| 輸出 | `out/dashboard.html`（gitignored） | 內含個人資料，不進版控 |

**為什麼不用 Streamlit**：它需要一個活著的 process。這個 dashboard 應該是「跑完排程就
生成一個檔案」，而不是「有一台服務要顧」——後者會在你最需要它的時候剛好沒開。

**為什麼不用 plotly**：它會把 3 MB 的 JS 塞進 HTML，而我們只需要五種圖。
自己畫 SVG 大約 300 行，換來的是可以直接當 artifact 發布、也不會有版本相容問題。
